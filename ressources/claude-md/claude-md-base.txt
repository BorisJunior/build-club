# Base CLAUDE.md - Rigueur de developpement

Ce fichier n'est pas une note decorative.
C'est le cadre permanent qui dit a l'agent comment il doit travailler.

Sans cadre clair, un agent peut :
- coder trop vite
- oublier les tests
- laisser des checks rouges
- casser l'architecture
- annoncer "c'est fini" trop tot

Avec un bon CLAUDE.md, tu imposes une discipline.

---

## Ce que le fichier doit imposer

### Qualite non negociable

- Pas de code jete vite fait sans verification.
- Pas de tache consideree comme terminee sans validation minimale.
- Pas d'over-engineering.
- Pas de complexite gratuite.
- Pas de solution fragile si une solution simple et robuste existe.

### Tests obligatoires

- Pas de code sans tests quand la stack et le projet s'y pretent.
- Si tu modifies un comportement existant, ajoute ou adapte les tests associes.
- Si le projet a deja une strategie de test, respecte-la.
- Si tu ne peux pas tester proprement, dis-le clairement.

### Checks verts avant de conclure

Avant de considerer une tache terminee, lance les commandes de verification pertinentes.

Exemple de base Python stricte :

```bash
uv run black .
uv run ruff check .
uv run mypy .
uv run pytest tests -v
```

Si un check echoue :
- tu corriges
- tu relances
- tu ne continues pas comme si de rien n'etait

### Typage

- Utilise le typage quand la stack le permet.
- Evite les types trop vagues quand une structure claire est possible.
- N'utilise des echappatoires qu'en dernier recours et seulement si elles sont justifiees.

---

## Architecture

Si le projet suit une architecture propre ou hexagonale, le fichier doit l'imposer clairement.

Exemple de regles utiles :

1. le domaine ne depend jamais de l'infrastructure
2. l'application peut utiliser le domaine, pas l'infrastructure directement
3. l'infrastructure implemente les ports du domaine

Le but n'est pas de reciter de la theorie.
Le but est d'empecher l'agent de melanger toutes les couches juste pour aller vite.

---

## Workflow de session

Un bon CLAUDE.md doit imposer une maniere de travailler.

Exemple simple :

1. comprendre la demande
2. identifier les zones du projet concernees
3. planifier rapidement
4. coder
5. expliquer les choix importants
6. ecrire les tests
7. lancer les checks
8. corriger si besoin
9. conclure seulement quand c'est vraiment valide

Quand la tache est un peu large :
- avance par sous-phases
- valide chaque sous-phase avant de passer a la suivante

---

## Expliquer pendant qu'on code

Le fichier peut aussi imposer a l'agent de ne pas coder en silence.

Avant de coder :
- dire ce qu'il va faire
- dire pourquoi il choisit cette direction

Pendant :
- signaler les choix techniques importants
- signaler quand il lance les checks

Apres :
- dire ce qui a ete fait
- dire les points d'attention

Ca force plus de rigueur et ca permet de detecter plus vite les mauvaises directions.

---

## Securite minimale

- Ne mets jamais de secrets en dur dans le code.
- Valide les inputs quand c'est pertinent.
- Evite les raccourcis dangereux "juste pour que ca marche".
- Respecte les bonnes pratiques de base de la stack utilisee.
- Si ca touche a l'auth, aux permissions, aux donnees sensibles ou au paiement, sois particulierement prudent.

---

## Definition de "termine"

Une tache n'est consideree comme terminee que si :

- le besoin a ete traite
- le code est coherent avec le projet
- les checks importants ont ete lances
- les erreurs eventuelles ont ete corrigees
- les tests necessaires ont ete ajoutes ou adaptes si pertinent
- rien d'important n'est laisse casse silencieusement

Si une partie n'a pas pu etre faite :
- tu le dis explicitement
- tu expliques pourquoi

---

## Ce qu'il faut toujours faire

- comprendre avant d'agir
- planifier avant de modifier
- tester avant de conclure
- respecter la structure existante
- rester coherent avec l'architecture
- demander si quelque chose est flou

---

## Ce qu'il faut eviter

- coder en silence
- ignorer les checks
- oublier les tests
- contourner la structure du projet pour aller vite
- declarer une tache finie alors que les checks sont rouges
- ajouter de la complexite juste pour faire "propre"

---

## Reflexe par defaut

Si tu hesites :
- choisis la solution la plus simple
- garde la solution lisible
- verifie avant de conclure
- prefere la robustesse a l'effet demo
